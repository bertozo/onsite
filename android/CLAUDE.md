# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

OnSite (package `com.xbertz.onsite`) — an Android app (Kotlin + Jetpack Compose) for a self-employed tradesperson in Australia to log work sessions per site (GPS or manual entry), keep clients/sites/job types, and generate invoice PDFs. UI strings live in `res/values*/strings.xml` in English (default), Portuguese (`values-pt`) and Spanish (`values-es`); **never hardcode user-facing text in Kotlin** — add a key to all three files. Code comments are in English.

The app is being migrated from fully local storage to a backend-backed, multi-platform architecture (backend in the sibling `onsite-backend` project; see its README). Room stays the on-device source of truth — the backend adds accounts, login and sync on top, it does not replace the offline behaviour.

## Build & run

- Open the project root in Android Studio and let it sync Gradle. `gradle/wrapper/gradle-wrapper.jar` is intentionally not committed; Android Studio generates it on first sync.
- CLI (Windows/Git Bash): the wrapper needs a JDK 17–21, e.g. `export JAVA_HOME="$HOME/.jdks/jbr-21.0.11"` (the JBR bundled with Android Studio is too new for Gradle 8.14). Then `./gradlew assembleDebug` or `./gradlew installDebug`.
- No test source sets yet; verification is a compile + install on the connected device (`adb` at `$LOCALAPPDATA/Android/Sdk/platform-tools/adb.exe`).
- Toolchain: Kotlin 1.9.24 (no K2), AGP 8.5.2, Compose BOM 2024.06.00 / compiler ext 1.5.14, Room 2.6.1 via **kapt** (not KSP), minSdk 26 / target 34, JVM target 1.8. Stay within those APIs when adding code or dependencies.
- Location is foreground only (`ACCESS_FINE_LOCATION`/`ACCESS_COARSE_LOCATION`); `INTERNET` is used only for address search. `CAMERA` is requested at runtime for the site-photo tool (CameraX 1.3.4, preview + capture both 4:3, preview letterboxed so the overlay can be laid on the frame rectangle); `WRITE_EXTERNAL_STORAGE` is declared only for API ≤ 28 to save stamped photos to the gallery.

## Architecture

MVVM, everything under `app/src/main/java/com/xbertz/onsite/`:

- `MainActivity.kt` — most Compose UI: `AppRoot` switches between `Screen` values (menu, tracker, reports, companies, sites, job types, profile, settings, planning, photo, invoices, invoice review); each screen is a composable in the same file, plus its dialogs. Exceptions: `ReportsScreen.kt` (reports), `InvoiceScreens.kt` (`InvoiceReviewScreen`, `InvoicesScreen`, PDF share/open helpers, `formatMoney`), `CompanySheet.kt` (bottom sheet per client). Shared building blocks (`AppTopBar`, `SectionHeader`, `EmptyState`, `InfoBanner`, `TrackerDropdown`, `SessionRateField`, `showDatePicker`, `EntityListItem`) are `internal` in `MainActivity.kt` so those files can use them. The home screen shows the running session with a chronometer (or a one-tap "resume last session") and a setup checklist; `SessionNotification.kt` posts an ongoing notification with the system chronometer while a session runs (no foreground service, `POST_NOTIFICATIONS` requested on API 33+). `MainActivity.attachBaseContext` wraps the context with `LocaleManager` (defined in `AppLocale.kt`, together with `AppLanguage`) so the chosen language applies before resources are read; a language change calls `recreate()` and `AppRoot` keeps the current screen via `rememberSaveable`. Theme colours live in `ui/theme/Theme.kt`.
- ViewModels are `AndroidViewModel`s, one per area: `LocationTrackerViewModel` (start/stop with GPS, manual sessions, edit/delete, `activeSession`/`lastSession`/`recentCombos` flows, `resumeLastSession`), `CompanyViewModel`, `SiteViewModel` (address search with debounce), `JobTypeViewModel`, `ProfileViewModel`, `InvoiceViewModel` (review request → PDF + persisted `Invoice` row, sequential number, status changes), `ReportViewModel` (column selection + report filters: period preset, company, unbilled-only; CSV export), `SettingsViewModel` (theme + language), `PlanningViewModel` (planned jobs per day; calendar navigation lives in `CalendarNavigator`/`CalendarUiState` in `CalendarState.kt`, rendered by the `CalendarPanel` composable), `PhotoViewModel` (site-photo tool: in-app CameraX capture from `StampCameraView`, stamped by `photo/PhotoStamper.kt` and saved to the gallery through MediaStore). The live overlay in `StampCameraView` and the final stamp share the geometry constants on `PhotoStamper` (`TEXT_SIZE_FRACTION`, `PADDING_FRACTION`, `LINE_HEIGHT_FACTOR`, `STROKE_FACTOR`, `LOGO_WIDTH_FRACTION`) and the line list from `PhotoViewModel.stampLines` — change them together or the viewfinder stops matching the saved photo. UI state flows out via `StateFlow`; screens never mutate state directly.
- ViewModel messages are **string resource ids** (`@StringRes Int` or `UiMessage(resId, args)`), resolved in the UI with `stringResource`, so they follow the app language. Code holding only an Application context uses `LocaleManager.resources(context)`.
- `data/` — Room (`onsite.db`, currently version 12, migrations in `AppDatabase`). Entities: `TrackingSession` (one row per session; `companyName`/`siteLabel`/`jobTypeLabel` stored **as text**; optional `hourlyRate` override and `invoiceId` once billed), `PlannedJob` (scheduled job for a day, same by-name references, optional fields), `Company` (optional default `hourlyRate`), `Site` (with lat/lon + address), `JobType`, `Profile` (single row, id = 1), `Invoice` (number, client by name, period, totals, status DRAFT/SENT/PAID/VOID, `pdfPath`, notes), `SyncMapping` (local id ↔ backend UUID per entity type, see `backend/SyncEngine.kt`). Effective rate of a session = its own `hourlyRate`, else the company's (`report/ReportSummary.kt` has `effectiveRate`, `summarize`, `weeklyTotals`, `totalsBySite`, `buildCsv`). `CompanyDao`/`SiteDao`/`JobTypeDao`/`TrackingSessionDao`/`PlannedJobDao` all have a `deleteById` alongside the entity-based `delete`, and their `insert` returns the generated row id — both exist for the sync engine, not the UI.
- Non-DB persisted state is in SharedPreferences: `settings` (`theme_mode`, `language`, `photo_timestamp_position`, `photo_label`, `report_columns`) and `invoices` (`next_invoice_number`, bumped by `InvoiceViewModel` after each PDF). Files in `filesDir`: `profile_photo.jpg`, `stamp_logo.png` (photo-tool logo; absence means "no logo"), `invoices/*.pdf` (generated invoices, path stored on the `Invoice` row).
- `invoice/` — `InvoiceData.kt` groups sessions into one `InvoiceLine` per worked day **and rate** (a day with two rate overrides becomes two lines; `sessionIds` link back) and exposes `valueFor(ReportColumn)`; `InvoicePdfTemplate.kt` renders the fixed A4 layout with Android's `PdfDocument` (no PDF library), printing Rate/Amount per line when any line has a rate, plus an optional notes block. PDFs go to `filesDir/invoices/` (CSV exports to `cacheDir/invoices/`); both are shared through the `FileProvider` declared in the manifest (`res/xml/file_paths.xml`). Flow: Reports or the company sheet call `InvoiceViewModel.startReview(...)` → `Screen.INVOICE_REVIEW` → `generateInvoice` inserts the `Invoice`, marks the sessions' `invoiceId` and the Reports screen shows a snackbar with Share; voiding clears `invoiceId` again.
- `report/ReportColumn.kt` — the single column template used by both the on-screen `ReportTable` and the PDF; enum order is display order, `DATE`/`HOURS` are always shown.
- `Validators.kt` — ABN (modulus-89 check), BSB, account number, phone, email; blank is valid (fields are optional).
- `AddressSearch.kt` — Photon (OSM) geocoder, restricted to Australia's bounding box.
- `backend/` — the client for `onsite-backend`. `BackendApi.kt` is a Ktor `HttpClient` (OkHttp engine) talking to `http://127.0.0.1:8080` (reach it from a real device with `adb reverse tcp:8080 tcp:8080`; cleartext to that address only is allowed by `res/xml/network_security_config.xml`); it has create/update/delete/list for every entity, all keyed by the backend's UUID, not the local Room id. `SessionStore.kt` keeps the JWT/email/account id in `EncryptedSharedPreferences`. `SyncEngine.kt` (`runSync`) is full-reconciliation, not delta/cursor: for each entity it diffs Room's current rows against `SyncDao`'s mappings to push (new local row → create; mapped row missing locally → was deleted, so delete remotely) and does the mirror image against the backend's list to pull (new remote row → insert; mapped remoteId missing from the list → delete locally). Order matters — invoices sync before sessions, both directions, so a session's `invoiceId` can be remapped through the invoice's own `SyncMapping` row. This same function *is* the first-login upload (a fresh account has no mappings, so everything already in Room looks "new" and gets pushed) — there is no separate one-time migration step. `AuthViewModel.kt` (root package) drives `AuthUiState` (`CheckingSession` → `LoggedOut`/`LoggingIn` → `SyncingData` on login → `LoggedIn`); `syncNow()` re-runs the same sync silently and is wired to `ON_RESUME` in `SignedInAppRoot` (`MainActivity.kt`), so other devices' changes show up next time the app is foregrounded, not instantly. `SettingsScreen` shows the signed-in email with a logout action. Login itself calls `POST /v1/dev/auth/login`, a **dev-only stand-in for Supabase Auth** that mints a session for any email with no password (see `onsite-backend`'s `DevAuthRoutes.kt`) — swap `BackendApi.devLogin` for the real Supabase SDK call once a project exists; nothing else in this flow needs to change, since the backend only ever verifies a JWT's claims.

## Things that are easy to break

- Sessions, planned jobs and invoices reference companies/job types **by name**. Renaming a company must call `TrackingSessionDao.renameCompany`, `PlannedJobDao.renameCompany` **and** `InvoiceDao.renameCompany` (the edit flow already does); job types need the session and planned-job equivalents.
- Sites are also referenced by `siteLabel`, and the report/invoice `ADDRESS` column is resolved by looking the label up in `sitesByLabel` (`buildInvoiceLines`). There is **no** `renameSite` yet — `SiteViewModel.saveEditedSite` only updates the `sites` row, so renaming a site silently drops the address for its past sessions. Add a rename query if you touch that flow.
- `ReportColumn` order and `InvoicePdfTemplate.columnSpecs` widths define the invoice layout; changing columns means updating both `valueFor` and the specs (and `buildCsv`).
- `CalendarUiState.dayHours` drives the planner heatmap; `CalendarDayCell` paints past days by hours and today/future days by planned jobs. Never `.copy(alpha)` a `Color.Transparent` marker (it turns black).
- Room schema changes require a new `Migration` in `AppDatabase` and a version bump; `exportSchema` is false.
- `LocaleManager` reads SharedPreferences `settings`/`language` synchronously — keep it cheap, it runs in `attachBaseContext`.
- The dev login (`DEV_AUTH_ENABLED`) must never be reachable outside a local backend; it grants a session for any email with no password at all.
- `SyncEngine.kt` decides "never synced" vs "deleted since last sync" purely from whether a `SyncMapping` row exists for a local id. Deleting a row through anything other than the DAOs (or a raw SQL edit) without going through `deleteById`/`delete` will not look deleted to the next sync — it'll just look untouched.
- Invoices have no `deleteById` (the app only voids them, never removes the row) — `pushInvoices`' delete-diff branch is a deliberate no-op kept for symmetry, not a gap.
- The resume-triggered `syncNow()` is silent and best-effort (`runCatching`); a failed sync never surfaces an error to the user, it just tries again on the next resume.
